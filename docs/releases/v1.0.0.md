# Agent Kernel v1.0.0 Release Notes

Status:

```text
Draft for final verification
```

Agent Kernel v1.0.0 is the first stable self-hosted AI Agent runtime release.

It is designed for developers and teams who want a production-shaped runtime
they can clone, run, inspect, extend, test, and deploy for self-hosted agent
systems.

v1.0 is not a hosted SaaS, no-code builder, third-party tool marketplace,
enterprise identity suite, or managed cloud platform.

## Positioning

Agent Kernel is a modular AI Agent runtime with:

- FastAPI API.
- Typer CLI.
- Durable worker process.
- LLM provider abstraction and model routing.
- Provider-native tool-call loop.
- Tool registry, policy checks, approvals, and auditability.
- RAG ingestion, retrieval, citations, embeddings, pgvector, and object storage.
- Scoped memory and task context.
- Auth, RBAC, workspace scope, and API-key authentication.
- Observability through structured logs, trace IDs, OpenTelemetry configuration,
  Prometheus-compatible metrics, and cost/usage records.
- Deterministic evals, persisted eval reports, release eval gates, and release
  smoke/load-soak commands.
- Next.js Agent Workbench for operator workflows.
- Docker Compose deployment baseline and production configuration docs.

## Who Should Use It

v1.0 is intended for:

- Engineers building self-hosted agent applications.
- Teams evaluating an agent runtime foundation for internal production pilots.
- Developers learning production-grade AI Agent architecture from a real
  deployable codebase.
- Contributors who want clear extension points for providers, tools, storage,
  retrieval, memory, evals, observability, and Web operator workflows.

v1.0 is not intended for:

- Public hosted multi-tenant SaaS workloads without additional platform
  hardening.
- Arbitrary untrusted code execution.
- Browser automation as a stable public product surface.
- Fully managed enterprise SSO deployments.
- Large-scale benchmark or leaderboard use cases.

## Highlights

Runtime and execution:

- Durable run lifecycle stored in the database.
- Worker loop for queued run execution.
- Worker leases and conservative stuck-run recovery.
- Retry and fallback visibility in persisted run timelines.
- Redis queue adapter foundation while keeping the database as source of truth.
- Provider-native OpenAI-style tool-call parsing, persistence, execution, and
  model/tool/model loop.

Tools, policy, and approvals:

- Tool interface, registry, JSON schema validation, and executor.
- Built-in safe tools.
- Risk levels and policy decisions.
- Persisted tool calls and audit timeline.
- Human approval records, approval API, approval CLI, and interrupt/resume.
- Approval authorization and workspace ownership checks.

RAG, storage, and memory:

- Knowledge bases, documents, ingestion jobs, chunks, and chunk embeddings.
- Local object storage and S3/MinIO-compatible object storage.
- Text/Markdown parsing and chunking.
- Mock embeddings and OpenAI embeddings.
- SQLite-compatible JSON-vector retrieval and PostgreSQL pgvector retrieval.
- Retriever, citation builder, retrieval API, retrieval CLI, and `kb_search`
  tool.
- Scoped short-term memory, task context, user preferences, and long-term
  memory.

Security and identity:

- Identity, workspace, role, permission, and API-key domain models.
- API-key hash storage.
- API-key authentication middleware.
- Route-level authorization baseline for stable `/v1/*` routes.
- Auth/RBAC documentation and security hardening checklist.

Observability and evals:

- Structured logs and trace IDs.
- Model, tool, retrieval, runtime, and API metrics.
- Prometheus-compatible `/metrics` endpoint.
- OpenTelemetry exporter configuration.
- Deterministic eval dataset format and runner.
- Release-blocking eval command.
- Persisted eval runs with API, CLI publish path, and Web Workbench views.

Operator experience:

- API, CLI, worker, and Web Workbench.
- Live Workbench paths for health, runs, approvals, knowledge bases, retrieval,
  and eval reports.
- Quickstart, production configuration, troubleshooting, backup/restore,
  upgrade/migration, security, release-gate, and clean-machine rehearsal docs.

## Upgrade Notes

Production deployments should use PostgreSQL.

Before running v1.0 application processes:

```bash
uv run alembic upgrade head
```

Recommended upgrade sequence:

1. Back up Postgres and object storage.
2. Stop workers.
3. Run migrations.
4. Start API.
5. Start workers.
6. Start or refresh Web.
7. Run smoke checks.

SQLite remains supported for local development and tests. It is not the
recommended production database.

See [Upgrade and Migration Policy](../upgrade-migration-policy.md) and
[Backup and Restore Guide](../backup-restore.md).

## Security Posture

v1.0 is suitable for self-hosted deployments where operators control network,
secrets, storage, and user access.

Production operators should:

- Set `AGENT_KERNEL_ENV=production`.
- Set `AGENT_KERNEL_API_KEY_AUTH_ENABLED=true`.
- Put API and Web behind HTTPS.
- Keep Postgres, Redis, object storage, and `/metrics` private or protected by
  gateway controls.
- Store API keys, database URLs, Redis credentials, OpenAI keys, and AWS-style
  credentials in platform secret storage.
- Review dependency advisories before publication and during operations.

See [Security Hardening Checklist](../security-hardening.md).

## Accepted v1.0 Limitations

These limitations are accepted for v1.0 because the release is scoped as a
self-hosted runtime:

- API-key authentication is disabled by default for local quickstart
  compatibility.
- Browser login, OIDC, SSO, and password auth are not included.
- The Web Workbench is not a full administration console.
- Public hosted SaaS tenant isolation is out of scope.
- `/metrics` has no built-in authentication and must be protected by network,
  reverse proxy, gateway, or platform controls.
- Secrets manager integration is deployment-specific.
- Remote sandbox execution is not implemented.
- Browser session automation is not implemented.
- Redis queue adapter support exists, but database-backed polling remains the
  default worker execution path.
- Stuck-run recovery is conservative and fails expired in-flight runs instead
  of automatically replaying every run.
- Server-side eval dataset upload, eval job scheduling, LLM-as-judge, and live
  provider eval execution are not part of the stable v1.0 surface.
- OpenTelemetry collector deployment, trace retention, dashboards, and alert
  policies remain operator responsibilities.
- Dependency advisories must be reviewed at release time and either resolved or
  explicitly accepted in the final release notes.

See [v1.0 Scope Freeze](../v1-scope-freeze.md).

## Deferred Beyond v1.0

These items are intentionally outside the v1.0 release and should not block
publication:

- Hosted multi-tenant SaaS.
- Multi-region managed cloud deployment.
- Full enterprise SSO and identity-provider administration.
- Fine-grained billing, quota, and usage-plan management.
- Third-party tool marketplace.
- Advanced multi-agent marketplace.
- Visual no-code workflow builder.
- Browser session automation product surface.
- Remote sandbox execution service.
- Cross-browser Web test matrix.
- Public performance dashboard.
- Large-scale benchmark leaderboard.
- Stable APIs for hybrid retrieval, RRF, reranking, query rewriting, and
  advanced retrieval pipelines.
- Stable APIs for server-side eval dataset management and eval job execution.
